## Why

P3 人工故障注入已经证明外部 MCP 失败能够被 Trace、Attempt、降级报告和人工重试闭环捕获，但验收同时暴露了三个会影响解释可信度的问题：诊断详情把多次执行的工具调用显示为未标注的累计值，最终报告会把历史案例内容混入当前结论，并且在 `recordCount=0` 时给出超出证据范围的推断。现在修复这些问题，可以让项目展示的不只是“能够重试”，而是“恢复过程可解释、报告结论可追溯、评测能阻止同类回归”。

## What Changes

- 在 AIOps 诊断详情中明确区分诊断任务累计指标和单次执行数据，为跨重试累计的步骤、证据和工具调用添加可理解的执行分组与标签。
- 在报告生成输入中区分本次执行证据、当前告警输入和历史案例参考，历史案例只允许影响排查计划，不能作为本次事实、症状或根因证据。
- 对 `recordCount=0`、工具失败和证据缺失采用谨慎结论：只陈述已观察事实和仍无法区分的可能性，不把“无匹配日志”直接等同为“采集链路异常”。
- 修复面向用户报告中的资源标识脱敏格式，继续保证 MCP URL、CLS Topic ID 和凭据不会泄漏。
- 为报告证据边界、谨慎结论和跨执行展示增加确定性测试与自动评测规则，并记录 P3.2 的问题发现、修复、验证和面试复盘材料。

## Capabilities

### New Capabilities

- `agent-evaluation-report-evidence`: 定义基于已保存 AIOps Trace 与报告的确定性证据边界评测，覆盖历史案例污染、无证据过度推断和资源标识脱敏。

### Modified Capabilities

- `aiops-diagnosis-ui`: 将跨重试累计数据明确标注并按执行分组，避免把诊断任务累计工具数误读为单次 Trace 工具数。
- `aiops-diagnosis-tasks`: 约束报告只能把当前告警输入与本次执行工具结果作为事实证据，历史案例仅作为计划参考，并在零结果时保持不确定性。
- `real-mcp-tools`: 规范面向用户的资源标识脱敏占位符，禁止多余标点和真实内部标识泄漏。

## Impact

- 后端 AIOps LangGraph 报告输入组装、报告提示与确定性回退报告。
- AIOps 证据链 API/前端类型与诊断详情的执行链、工具调用展示。
- 自动评测规则目录、Dataset fixture、评分结果与相关 API/CLI 测试。
- 后端 pytest、前端 Vitest、OpenSpec 与 Markdown 版本复盘文档。
- 不新增外部依赖，不改变真实 MCP/CLS 集成方式，不扩展为通用分布式恢复平台。
