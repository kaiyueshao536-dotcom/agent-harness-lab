## Context

P3 的一次诊断任务在人工重试后会复用 `diagnostic_task` 资源，并为每次后台执行创建独立 Agent Trace；但诊断步骤、证据和工具审计仍按任务累计返回。当前前端直接渲染累计数组，因此三次执行会显示 6 次工具调用，却没有说明每次 Trace 实际只有 2 次。另一方面，Planner 检索到的历史诊断案例内容被直接传给 Report LLM，导致历史症状进入当前报告；当 SearchLog 返回零记录时，LLM 还可能把“没有匹配日志”扩写为“采集链路异常”。

本次修改涉及后端证据链 API、LangGraph 报告生成、前端执行链和自动评测，但不需要新增外部服务或数据库迁移。已有 Trace 已包含资源 ID、状态、起止时间和耗时，步骤与工具审计也包含时间戳，可以为历史数据派生执行分组。

## Goals / Non-Goals

**Goals:**

- 让诊断任务累计数据与单次 Trace 数据在界面上可区分、可解释。
- 确保历史案例只影响 Planner，不成为当前症状、日志或根因的事实来源。
- 对工具失败和 SearchLog 零结果生成确定性、谨慎、已脱敏的报告。
- 让自动评测可以确定性阻止零结果场景中的过度推断，并能用现有排除规则阻止已知历史污染词。
- 保留 P3 原有的真实 MCP、Attempt Trace、人工重试和历史执行记录。

**Non-Goals:**

- 不实现通用分布式恢复编排、跨服务 Saga 或自动补偿平台。
- 不新增 LLM-as-a-judge，不让评测依赖模型或外部网络。
- 不尝试从零结果自动判定 CLS Topic、查询条件、时间窗口或采集链路中的具体故障位置。
- 不删除旧 Trace、步骤、工具审计或报告。

## Decisions

### 1. 由 Trace 时间边界派生诊断执行分组

证据链 API 将按 `resource_type=diagnostic_task` 和 `resource_id=task.id` 查询所有 AIOps Trace，并按开始时间排序。每个分组返回 Trace 摘要，以及时间落入该 Trace 起止区间的步骤 ID 和工具调用 ID。前端默认展示所有分组，但把标题、状态、耗时、单次工具数和 Trace ID 放在每个分组上；顶层只显示“跨 N 次执行累计”。

选择这一方案是因为现有数据已足够支持顺序重试，不需要给步骤和工具审计新增列或迁移 SQLite。替代方案是在所有表增加 `trace_id`；它长期更直接，但会扩大 P3.2 的迁移、兼容和测试范围。若未来允许同一诊断并发执行，再升级为显式外键。

### 2. Planner 参考与 Report 事实输入分离

Planner 继续使用 owner 范围内的 SOP/历史案例生成排查计划；Report 输入不再携带历史正文，只携带当前诊断 Query、当前告警、执行计划和本次执行工具证据。报告可以说明是否使用通用计划或参考来源名称，但不得把参考正文中的症状、日志和根因写成当前事实。

替代方案是让 LLM 在同一个上下文中自行区分“历史参考”和“当前证据”；人工验收已经证明该提示约束不可靠，因此不采用。

### 3. 证据不足时绕过自由生成

当本次执行失败，或所有成功 SearchLog 结果均为 `recordCount=0` 时，Report 节点直接使用现有确定性 Markdown 回退报告。回退报告只陈述“当前查询没有匹配到可解析日志”，列出尚不能区分的原因，并明确“证据不足，无法确认根因”。只有存在可解析执行证据时才调用 LLM。

这会减少零结果场景的生成灵活度，但换来可复现、可评测和可面试解释的安全边界。

### 4. 增加确定性谨慎证据规则

自动评测新增 `evidence_cautious` 规则。该规则只检查持久化报告文本：当报告包含零结果信号时，必须同时包含证据不足/无法确认语义，并不得包含“表明采集链路异常”“证明 Topic 无数据”等确定性因果表述。历史污染的具体词由 Dataset 使用现有 `excludes_all` 规则声明。

规则保持纯函数和离线可运行，不访问数据库、模型、MCP 或云服务。

### 5. 脱敏后统一清理占位符边界

资源标识替换完成后，将占位符后因原始括号残留产生的重复 `]`/`】` 归一化为一个完整占位符。测试同时覆盖真实 Topic ID、URL 和凭据不出现在文本中。

## Risks / Trade-offs

- [历史步骤时间戳恰好落在 Trace 边界外] → 使用相邻 Trace 开始时间作为上界，并为无法归属的数据保留“未归属历史记录”分组，不丢数据。
- [同一诊断未来并发重试导致时间窗口重叠] → 当前后台任务只允许终态后重试；在 API 测试中固定该前提，未来并发需求改用显式 `trace_id` 外键。
- [确定性谨慎规则无法理解所有中文表达] → 只覆盖可解释的高风险模式，并允许 Dataset 用 `contains_all`/`excludes_all` 增补业务词；不宣称完成通用事实核验。
- [零结果回退报告减少 LLM 生成内容] → 这是有意的安全取舍；报告仍包含结构化章节、已执行步骤和后续验证建议。

## Migration Plan

1. 先扩展后端证据链响应并保持现有字段不变。
2. 更新共享 TypeScript 合同和前端分组展示，旧字段继续兼容。
3. 调整 Report 输入与零结果回退策略，补齐脱敏测试。
4. 增加评测规则、前端选择项与离线/服务测试。
5. 运行 OpenSpec、pytest、Ruff、Pyright、前端测试和构建。
6. 若需要回滚，切回 P3.1 Tag；本次无数据库迁移和不可逆数据操作。

## Open Questions

- 当前不处理并发执行；若未来后台 Runtime 允许同一诊断并发重试，需要为步骤、证据、报告和工具审计增加显式 `trace_id`。
