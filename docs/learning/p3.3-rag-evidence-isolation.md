# P3.3：AIOps RAG 证据隔离与 Context Snapshot

## 这次解决的真实问题

一次真实支付告警诊断中，知识检索返回了三条高相关结果：一份正确的支付超时 SOP，以及两份以前自动保存的诊断案例。工具调用和当前 CLS 日志均成功，但最终报告仍写入了历史案例里的“`MCP server unavailable`”和零日志结论。

这说明问题不主要在 Chat 长对话记忆，而在 AIOps Planner 的知识角色边界：正式 SOP 和历史诊断案例共用知识库，旧实现只按相关度取前三条，导致历史结论在规划阶段进入当前上下文。

## 闭环过程

1. **复现**：选中 `PaymentGatewayTimeoutHigh`，确认当前 Trace 中知识检索和 SearchLog 都成功。
2. **取证**：检查引用，发现正确 SOP 分数约为 `0.8978`，两条历史诊断案例分数约为 `0.7644` 和 `0.7396`。
3. **定位**：Planner 使用 `top_k=3`，没有 `knowledgeType` 过滤；报告提示词边界修复得太晚，污染已经进入计划。
4. **修复**：Planner 固定使用 `knowledgeType=sop`；过滤发生在 Rerank 之前。历史案例继续保存，但不再进入默认规划上下文。
5. **解释**：Planner step 保存安全的 `retrievalContext`，展示策略、过滤条件、来源、知识角色、分数和退化原因，不保存 chunk 正文或提示词。
6. **防回归**：混合语料单测证明历史案例不会进入 Rerank；P3.3 离线 Dataset 同时要求正确告警/服务/SOP，并排除已知污染词。

## 为什么不用相似度阈值

阈值解决的是“相关性够不够”，不能回答“这条知识可以扮演什么角色”。一条错误历史案例可能与当前告警非常相似，分数甚至高于正式 SOP。`knowledgeType=sop` 是明确的业务边界，比调一个难以解释的分数阈值更稳定。

## Context Snapshot 是什么

它是某次 Planner 检索决策的有限快照，回答：

- 用什么查询和策略；
- 允许、排除了哪些知识角色；
- 命中了哪些文档，来源、角色和分数是什么；
- 没命中或检索失败时为何退化。

它不是模型思维链，也不复制提示词和知识正文。面试时可以把它解释为“为检索决策补充可审计的输入来源清单”。

## 如何运行离线 Gate

在 `apps/backend` 执行：

```bash
uv run super-ai-eval ../../evals/fixtures/p3.3-rag-evidence-isolation-pass.json
```

该 Gate 使用现有确定性规则：`trace_succeeded`、`required_tools`、要求正确告警/服务/SOP 的 `contains_all`，以及排除本次真实历史污染词的 `excludes_all`。

它能防止已知问题回归，但不能发现所有未知事实错误。新的污染模式仍需要人工验收发现，再决定是否转成 Dataset 规则。

## 手工复测重点

重新运行 SOP seed，让既有文档获得 `incidentId`、`alertName`、`service` 和 `sopId` 元数据；随后重新执行支付告警诊断。在执行链 Planner 中应看到 `SOP-only`，所有命中项角色均为 `sop`，报告不得出现与当前 Trace 冲突的历史失败结论。
