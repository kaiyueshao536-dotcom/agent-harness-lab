# P3.2 报告证据边界评测

这份说明用于在“自动评测”页面建立一个可复现的 P3.2 Dataset。它不使用 LLM Judge，而是把本次人工故障注入发现的两个具体风险写成确定性规则：零日志结果不得被扩写为确定性故障结论，当前 CLS 连通性任务不得混入历史结算服务症状。

## 推荐 Dataset

| 字段 | 建议值 |
| --- | --- |
| 名称 | `P3.2 恢复证据质量集` |
| 版本 | `v1` |
| 通过率门禁 | `100%` |
| 平均分门禁 | `100%` |
| 最大耗时回退 | 根据面试演示是否考察性能决定；证据质量集可暂不设置 |

创建一个 AIOps Case，输入摘要写成“验证当前配置的 CLS Topic 是否可以查询，无结果时保持证据不足”。依次暂存以下规则：

1. `trace_succeeded`
2. `required_tools`，期望值为 `SearchLog`
3. `evidence_cautious`
4. `excludes_all`，期望值为 `结算服务 API 延迟升高,采集链路存在异常`

运行时绑定修复后生成的成功 AIOps Trace。仓库内无密钥的离线等价样例位于 [`evals/fixtures/p3-report-evidence-pass.json`](../../evals/fixtures/p3-report-evidence-pass.json)。

## 规则解释

- `trace_succeeded` 只证明程序执行完成，不证明报告正确。
- `required_tools` 证明当前 Case 确实走过 SearchLog，而不是只凭模型回答。
- `evidence_cautious` 在报告包含 `recordCount=0`、未返回日志或未匹配日志时，要求报告同时承认证据不足，并拒绝确定性采集链路/Topic 结论。
- `excludes_all` 把本 Case 已知的历史污染词显式写进考试卷。它不是通用语义理解，只是对真实回归风险的确定性保护。

## Gate 仍然不知道什么

这个 Dataset 不能自动发现所有未知事实错误。新的历史案例如果使用了未被列入 `excludes_all` 的其他症状词，仍可能逃过该规则；`evidence_cautious` 也只覆盖明确的零结果高风险表述。因此评测结果必须与 Trace、Tool Audit 和人工报告审查结合使用。

面试时可以这样解释：先由人工验收发现“Gate 100% 通过但报告混入历史症状”，再把已知风险转成确定性 Dataset 规则；同时明确规则能力边界，不把关键词检查包装成通用事实核验。
