## 背景与真实问题

P3 的自动化测试已经证明 Tool、Attempt、Job 重试和 Trace 能工作，但亲自进行 MCP 故障注入时又发现 5 个影响演示和排障的问题：

1. 失败诊断已经生成降级报告时，页面没有显示“重试本次诊断”。
2. Span 时间线只按顺序平铺，无法快速看出 `aiops.graph → SearchLog → SearchLog.attempt`。
3. 两个 Attempt 可见，但页面没有显示尝试序号和最大次数。
4. 失败报告把 MCP 内部地址和 CLS Topic ID 暴露给了普通报告读者。
5. 告警源配置中一个未启用的空占位源仍参与校验，导致有效的本地 Alertmanager 被连带判定为不可用。

这些问题不是为了增加架构复杂度而虚构的需求，而是从“功能存在”走到“用户能正确使用和解释”时暴露的真实缺口。

## 根因与修复

| 问题 | 根因 | 修复 |
| --- | --- | --- |
| 降级报告没有重试入口 | 报告分支比失败分支优先，重试按钮只存在于无报告失败态 | 失败状态优先；报告标题显示“失败后的降级报告”；重试动作独立于报告是否存在 |
| Span 层级不清楚 | UI 只使用 `sequence`，没有消费 `parentSpanId` | 从父链计算 `depth`，按层级缩进，并用 `↳` / `↳↳` 显示父子路径 |
| Attempt 元数据不可见 | Trace 已保存 attributes，但组件没有白名单展示 | 只展示 `attemptNumber`、`maxAttempts`、`attemptCount` 和 `errorCategory` |
| 历史报告泄露内部标识 | 新报告生成链路做了处理，但 Evidence Chain 读取 API 使用另一套序列化函数 | 统一公开序列化出口；正文和嵌套 payload 在返回浏览器前递归脱敏；原始错误只留在 Tool Audit |
| 告警订阅一直失败 | 未启用的配置占位源仍先执行必填字段校验 | 增加显式 `enabled` 开关，先过滤禁用源，再构建真实 provider |

## 关键设计决策

- **Trace 只展示白名单属性**：不把所有 attributes 直接渲染到页面，避免 URL、参数、结果和凭据随可观测数据外泄。
- **读取出口也必须脱敏**：不能只保证新数据安全写入；历史数据、迁移前数据和其他读取 API 都要经过同一公开序列化边界。
- **原始错误和公开错误分层**：Tool Audit 保存排障凭证，Trace 与报告只暴露工具名、错误类别和可执行提示。
- **禁用配置不参与校验**：模板可以保留外部 Prometheus 示例，但本机只启用实际可访问的 Alertmanager。
- **不覆盖旧失败记录**：恢复重试创建新 Job 和新 Trace，旧失败记录继续作为审计证据。

## 真实验收证据

故障任务：`diagnostic_8d165dd104d14e329853b1103453280e`。

| 项目 | 失败执行 | 恢复执行 |
| --- | --- | --- |
| Job ID | `job_881d79003265493390be77c66e1fb175` | `job_575bc45f1b99459ca0e8ecd3f0fff85d` |
| Job 状态 | failed | succeeded |
| retryOfJobId | 无 | 指向失败 Job |
| Trace ID | `trace_ba450307f1e7428ea80f0e823353114c` | `trace_3bac5084bbdb49448a18839ff2f7c100` |
| Trace 状态 | failed | succeeded |
| Trace 耗时 | 69,436 ms | 85,571 ms |

页面验收结果：

- 失败任务同时显示“失败后的降级报告”和“重试本次诊断”。
- Trace 明确显示 `↳ SearchLog` 以及两条 `↳↳ SearchLog.attempt`。
- Attempt 分别显示“第 1/2 次尝试”和“第 2/2 次尝试”。
- 历史失败报告中的 MCP 地址与 Topic ID 被替换为公开占位文本。
- Alertmanager 返回空数组时，页面显示“当前告警源没有返回活跃告警”，不再误报加载失败。
- 恢复 MCP 后点击重试，约 86 秒产生成功 Job 和成功 Trace。

## 面试讲法

1. 自动化测试说明 P3 核心状态机能运行，但手工故障注入发现“能运行”和“能排障”之间还有 UI 与安全缺口。
2. 先用 Trace 和页面复现，再把问题拆成状态优先级、父子数据消费、公开序列化和配置选择四类根因。
3. 修复时没有扩展成通用分布式恢复平台，只补真实 MCP 故障链路需要的边界。
4. 新增回归测试时，测试又抓到 JSON payload 中裸 `topicId` 没被文本正则处理，于是补成字段感知的递归脱敏。
5. 最后恢复 MCP，通过新 Job、新 Trace 和 `retryOfJobId` 证明问题已经闭环，而不是只验证按钮出现。

## 已知限制

- 后台 Runtime 仍与 FastAPI 同进程，不提供多节点 worker 的故障接管。
- 当前重试整个诊断 Job，不支持从任意 LangGraph 节点安全续跑。
- Tool Audit 面向拥有该诊断权限的排障用户，仍需按最小权限控制访问。
- Alertmanager 空状态只说明接口可用且当前无活跃告警，不代表上游告警规则一定完整。
