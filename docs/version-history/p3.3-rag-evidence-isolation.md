## 背景与真实问题

真实支付超时诊断中，当前 SearchLog 和 MCP 均成功，检索也命中了正确 SOP，但报告仍混入早期诊断案例中的 MCP 失败和零日志结论。取证发现 Planner 的前三条结果同时包含一份正式 SOP 和两份自动沉淀的 `diagnostic-case`。P3.2 只阻止历史正文直接进入 Report，尚未阻止它在 Planner 阶段影响当前执行。

## 实现内容

- 知识文档上传增加受控检索元数据；普通用户只能声明 `document` 或 `sop`，不能伪造历史案例或 owner/tenant。
- 索引将 incident、alert、service、SOP 和服务器控制的案例来源字段传播到每个 chunk，作用域字段仍由服务器覆盖。
- Java 电商 SOP seed 显式提交关联元数据，便于重新索引后按来源解释。
- AIOps Planner 构造告警关联查询，并固定应用 `knowledgeType=sop` 过滤；历史案例在 Rerank 之前被排除。
- Planner step 持久化有限的 `retrievalContext`，前端显示 SOP-only 策略、角色边界、命中来源、分数和 fallback reason。
- 新增混合 SOP/历史案例测试与无密钥 P3.3 离线 Gate。

## 关键设计决策

- **按角色过滤，不调相似度阈值**：高相关历史案例仍可能是错误当前事实，相关性不能代替知识角色。
- **复用现有 Milvus collection 和 metadata filter**：不拆 collection、不迁移数据库，保持项目可讲清楚和复现。
- **历史案例保留但默认不参与 Planner**：未来若引入案例辅助，需要单独通道和冲突校验。
- **Snapshot 只保存来源摘要**：不保存 prompt、chunk 正文、思维链或凭据。
- **继续使用确定性 Gate**：针对已观察到的污染词和必需事实，不包装成通用事实核验器。

## 安全与成本边界

- 上传白名单拒绝 owner/tenant、案例身份和未知字段；服务器作用域始终优先。
- Context Snapshot 不含检索正文、完整提示词、模型思维链、MCP URL、Topic ID 或密钥。
- 离线 fixture 不连接模型、Milvus、MCP 或 CLS，不产生云端费用。
- 真实手工复测仍会查询 CLS，可能产生对应云服务用量。

## 已知限制

- 已存在的 SOP 虽然通常已有 `knowledgeType=sop`，但要获得完整 incident/service 元数据仍需重新运行 seed。
- P3.3 Gate 只能检测 Dataset 声明的事实和污染词，不能自动发现所有幻觉。
- 历史案例辅助规划尚未重新开放；后续若需要，应设计独立召回、来源标记和冲突处理，而不是重新混入 SOP 通道。
- P4 才会系统比较 Context Snapshot、Token 预算、无关上下文识别和不同上下文策略的质量/耗时。
- 在已有 Dataset 留有 Trace 绑定时直接创建并运行新 Dataset，前端会暂时保留旧 Case 的绑定，后端会正确拒绝这组多余 Case ID；重新选择数据集可清空绑定。该问题不影响评分正确性，但应作为后续前端状态清理修复候选。

## 复盘结论

P3.3 把“报告被历史内容污染”从主观感觉变成可定位的数据边界问题：先用 Trace、引用和分数取证，再在 Rerank 前隔离知识角色，通过 Snapshot 解释实际输入，最后把真实失败词写入 Gate。技术范围不大，但完整体现了复现、定位、修复、验证和防回归闭环。
