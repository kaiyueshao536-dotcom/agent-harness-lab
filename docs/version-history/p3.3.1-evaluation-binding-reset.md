## 背景与目标

在 P3.3 真实 Trace 验收中，用户先在 P0-P2 Dataset 绑定了两条 Trace，再创建 P3.3 Dataset。新 Dataset 首次运行提交时，前端仍把旧 Case ID 一并发送，后端按精确 Dataset 边界返回 400。重新切换一次 Dataset 后绑定被清空，运行恢复正常。

目标是让“创建 Dataset”和“切换 Dataset”具备相同的运行草稿隔离语义，同时保留后端拒绝外来 Case ID 的保护。

## 实现内容

- 在 `EvaluationView.vue` 增加集中式 `resetRunDraft()`。
- Dataset 创建成功与显式切换后统一清空 `traceBindings` 和 `baselineRunId`。
- 保留 `candidateLabel`，避免与问题无关的输入丢失。
- 新增组件测试，完整覆盖“旧绑定和旧基线 → 创建新 Dataset → 选择新 Trace → 首次运行”的顺序，并断言请求只包含新 Case ID。
- 不修改后端 API、数据库、评分规则和严格绑定校验。

## 关键设计决策

- 运行草稿属于 View 表单状态，因此在 View 层集中重置，不扩大 Pinia store 接口。
- Baseline 必须属于同一不可变 Dataset，创建新 Dataset 后不能猜测复用。
- 前端清理负责用户体验，后端精确校验仍负责最终一致性，二者不能互相替代。

## 安全与成本边界

- 修复不读取或记录访问令牌、Topic ID、CLS 凭据或原始日志。
- 测试使用内存 fake client，不调用模型、MCP 或 CLS，不产生云端费用。
- 后端继续拒绝包含目标 Dataset 之外 Case ID 的运行请求。

## 已知限制

- 本版本只修复 Dataset 范围的运行草稿，不实现跨 Dataset Baseline 迁移。
- Dataset 创建表单自身的未提交内容不属于运行草稿，关闭和重新打开时仍维持现有行为。
- P4 将作为独立版本治理上下文质量、Token 预算和无关上下文识别。

## 复盘结论

这个问题不是复杂算法错误，而是异步页面中常见的跨实体状态泄漏。通过真实操作发现、后端错误取证、最小状态归属分析和组件回归测试，形成了适合面试讲解的小型问题闭环。
